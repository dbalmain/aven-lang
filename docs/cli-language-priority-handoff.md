# Aven language ergonomics — prioritized implementation handoff

This handoff comes from a design review of `std/cli` at clean commit `12547d7`.
The user requested a file Claude can use to implement the recommendations.
No implementation was performed during the review. The priorities below are
recommendations, not claims that every proposed syntax or semantic detail has
already been approved.

Read `/home/dave/w/clex/.ai/core.md` first, then the current language spec at
`/home/dave/w/clex/docs/language-spec.md`. Recheck the current implementation:
the review distinguishes intended language semantics from features actually
implemented at the reviewed commit.

## Scope and settled decisions

- Primary objective: make Aven more comfortable for substantial library
  implementations while preserving its typed, expression-oriented model.
- Completion scripts are generated at runtime on an explicit route and installed
  once. TAB must never start Aven. Do not reopen this delivery decision.
- Value domains, positionals, and short bundles remain out of scope.
  `Meta.valueCompletion` is the seam for future value domains.
- Preserve typed decoder results, heterogeneous parsed records, explicit command
  constructor callbacks, and closed command-result variants.
- Never push. This handoff does not request a commit or deployment.
- Prior review accepted the reported green gates (1798 tests) without rerunning
  them. Run appropriate checks for actual implementation changes.

## Priority 1 — Guard / early-exit language design

**Evidence:** `crates/aven-host/std/cli.av`, `tokenizeGo` (reviewed lines 53–81).
The successful path nests through bounds checking, `--`, option lookup,
duplicate detection, arity, attached values, and next-token lookup. Each rejected
condition moves the continuing computation farther right.

**Recommendation:** add a small guard or early-return form. The spec explicitly
leaves this question open pending real programs; this tokenizer is sufficient
evidence to revisit it. An `if` expression alone would improve Boolean syntax
but would not flatten the continuing path.

**Design constraints to resolve before implementation:**

- Keep blocks expression-valued.
- Make the exit destination explicit and predictable: a nearest-function
  boundary is the recommended default.
- Define interaction with `?^`, nested lambdas, and record comprehensions.
- Avoid introducing mutable loops as part of this work. Recursion and the
  presentation of early exits are separate issues.
- Choose concrete syntax against the current grammar and formatter; this
  review did not settle a spelling.

**Acceptance:** rewrite the tokenizer to keep its continuing path shallow,
preserving all parsing/error behavior. Exercise exit typing, nested function
boundaries, propagation, formatting, and diagnostics. Keep the spec and tooling
consistent with the implemented form.

## Priority 2 — Implement raw and multiline text literals

**Evidence:** static shell programs in `bashStartLines` and the other `*Lines`
helpers are arrays of heavily escaped strings. Reviewing shell semantics
requires first mentally decoding Aven escapes.

Raw `r"..."`, raw triple-quoted, and interpolated triple-quoted strings are
already described in the language spec, but the reviewed lexer implements
neither raw nor triple-quoted strings. Worse, `push_unterminated_string` in
`crates/aven-parser/src/lexer.rs` recommends raw strings as a remedy.

**Recommendation:** implement the specified literal forms before inventing a
templating abstraction. Settle indentation and leading/trailing-newline behavior
explicitly. Exact preservation is the simplest baseline; any trimming needs a
precise, tested rule.

**Acceptance:**

- Support the forms through lexing, parsing, checking, evaluation, and formatting.
- Raw literals preserve backslashes and `${...}` literally; normal multiline
  literals retain normal escapes and interpolation.
- Verify embedded quotes, interpolation boundaries, line endings, indentation,
  unterminated forms, and formatter preservation of the resulting text.
- Convert static shell fragments where this materially improves readability.
  Preserve generated bytes or verify intentional differences in real shells.
- Keep `bashQuote` and `fishQuote`: source literals do not replace target-language
  escaping.
- Stop diagnostics recommending unavailable syntax, even if implementation is
  split across commits.

## Priority 3 — Narrow accidental-shadowing restrictions

**Evidence:** local `option` and `command` bindings collided with module-level
constructors, producing `name.accidental-shadowing`. The repaired generators use
`entry` and `item`. A larger module reserves more natural local names.

The existing diagnostic correctly points to both bindings and recommends `:=`
or renaming. The historical failure was not running the checker, not a failure
to diagnose the collision.

**Recommended semantic change:** allow function-local bindings to shadow
module-level values by default while retaining explicit rebinding for existing
bindings within the function's local scope.

**Resolve deliberately:** parameter shadowing, imported and builtin names,
enclosing-function captures, nested lambdas, recursive helpers, and the meaning
of `:=` when a module binding is visible. Do not silently generalize this proposal
to every nested scope or to type names.

**Acceptance:** local element names can be natural without disabling protection
against accidental local rebinding. Name resolution, inference, runtime lookup,
LSP behavior, diagnostics, and the spec agree on the boundary. Include cases
where a hidden module function would otherwise be called.

## Priority 4 — Make comptime limitations diagnosable

**Evidence:** `docs/cli-args-done.md` records failures involving ordinary text
computation at comptime, structured descriptors, and sibling-derived annotations.
The current spec promises known-argument evaluation and lifting the evaluated
result to its literal type. The working CLI demonstrates shape-driven
specialization more strongly than general comptime execution.

**Recommendation:** distinguish these cases in diagnostics and implementation
status:

- An input is genuinely runtime-dependent.
- A value is known, but the evaluator/bridge does not support the computation or
  representation yet.
- Evaluation fails or exhausts fuel.

Do not treat every `comptime.argument-not-known` as evidence that the user's API
must change. Preserve an actionable call path and source context, including
imported helpers, without using foreign spans as caller-file offsets.

**Acceptance:** reproduce the historical probes against current code first;
use the actual outcomes to add focused diagnostic regressions. State clearly
which promises are implemented. General comptime execution/residualization is a
separate project, not a prerequisite for shipping these completions.

## Priority 5 — Fix confirmed Bash scanner holes and extend focused coverage

This is a bounded correctness slice and can be implemented independently of the
language priorities above. Source: `bashStartLines` in `std/cli.av` and the real
Readline harness in `crates/aven-cli/tests/cli_args.rs`.

Use the existing `completion_tool.av` fixture. Its `add` command has `--verbose`,
`--chatty`, `--quiet`, `--out`, and `--output`. After an output value is consumed,
the remaining long candidates are `--verbose`, `--chatty`, and `--quiet`.

### Confirmed through real interactive Readline

TAB is at the end of each input:

| Input | Expected | Observed |
|---|---|---|
| `tool add >out --` | All add options; redirection is not an argv element | No candidates |
| `tool $'add' --` | Same options as `tool add --` | No candidates |

The scanner treats `>out` as an argument. For ANSI-C quoting, it retains `$`
before ordinary single-quote handling and produces `$add` instead of `add`.
ANSI-C quoting requires its actual escape semantics, not simply dropping `$`.
Reference: https://www.gnu.org/software/bash/manual/html_node/ANSI_002dC-Quoting.html

### Confirmed directly in the callback; validate through multiline Readline

These examples contain a physical backslash-newline:

```bash
tool add --out \
 --ver
```

The callback offers `--verbose`, although `--ver` is in a pending value position
and should receive no candidates.

```bash
tool \
 add --
```

The callback produces no candidates, although it should recognize `add`.

Cause: the backslash sets `started=1`; the newline is discarded; the following
space then emits a phantom empty argument. A removed line continuation must
not itself start a word. Preserve real empty arguments from `''` and `""`.
Reference: https://www.gnu.org/software/bash/manual/bashref.html

### Hypothesis to reproduce, not an established end-to-end failure

```bash
tool add --out $(printf "value") --
```

The substitution produces one value; the remaining flags should be offered if
this form is supported. Static inspection predicts that the scanner splits
inside `$()` and rejects source tokens. This exact input was not run in review.

The tested `$(printf "two words")` variant produced no candidates, but unquoted
expansion also creates an extra positional argument, so that test does not
demonstrate an observable completion bug. Do not cite it as a failing regression.

### Negative findings to preserve

Both `:; tool add --` and `true && tool add --` returned correct candidates
through real Readline. Direct callback probes misleadingly suggested failures.
Do not add command-separator fixes based only on invented completion variables.

**Implementation boundary:** never `eval` command-line text or execute user
expansions to recover argv. Define a conservative policy for unresolved
expansions. Recognize their syntactic boundaries rather than interpreting their
source as ordinary literal words. Arbitrary expansion results cannot generally
be known without execution.

**Acceptance:** exercise confirmed defects through the existing real-shell
harness; retain quoting/injection, empty-value, `=`, aliases, duplicate-option,
pending-value, and filename-fallback behavior. Keep parser implementation details
out of user-facing completion flows. Qualify the library's promise of following
argv semantics where expansions are deliberately unsupported.

## Priority 6 — Consider a scoped Result propagation expression

**Evidence:** `define` immediately invokes a zero-argument lambda so `?^` can
return an error locally before usage text is appended. This is a legitimate
scope boundary expressed through function construction and invocation.

**Recommendation:** after settling early exits, assess a `try`/`attempt`-style
expression that provides the same propagation boundary. No spelling was settled.
Keep this optional unless more examples justify it.

`Result.mapErr` already exists. Use it where appropriate before claiming explicit
`@Ok`/`@Err` reconstruction proves a missing language feature. The remaining
question is whether delimiting propagation must require a lambda.

## Priority 7 — Improve library representations using existing facilities

- `app` constructs separate metadata, parser, and help arrays whose indices must
  align. Investigate a single array of records containing those fields. The
  review did not prove Aven prevents that representation. If it fails, isolate
  the real typing limitation before proposing a compiler change.
- Repeated `Array.range(...).map(...)` plus indexing suggests an indexed mapping
  combinator in the Aven library layer. Inspect both native and ambient methods
  first. Do not add dependent-index machinery or new iteration syntax for this.
- Do not assume every annotation or fallback in the current library is forced
  by the type system; verify with a minimal example.

## What to preserve and what not to infer

The typed schema-to-parser path is the strongest positive result. Keep
heterogeneous values in records and project homogeneous metadata for traversal.
Explicit command constructors are useful, inferable ceremony. The general
compiler improvements this library motivated (`valuesOf`, specialization, and
joining function results) are evidence for the architectural direction.

This review did not establish a need for mutable loops, a separate agent syntax,
explicit block delimiters, dependent array bounds, automatic command-tag naming,
or a general templating framework. It also did not reverify the claim that this
is the largest real Aven program or independently reproduce all reported gates.

Work in reviewable slices. For language changes, update the canonical spec and
test the full affected path, not just parsing. For shell changes, make real
Readline/fish behavior the arbiter. Keep unverified hypotheses labeled until
reproduced.
