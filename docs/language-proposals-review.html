01
Language change

Make the continuing path shallow

Withdraw early-return recommendation

Add an explicit early-exit form. Keep expression-valued blocks and make the nearest function the exit boundary.

After your review · Withdraw early-return recommendation

Your objection is correct. A focused lookup implementation using Result matches and ?^ checked and ran successfully for success, unknown-option and duplicate-option paths. This example does not establish a need for non-error early return. Keep current control flow unless a stronger example emerges.

Your response

In the example you've provided, and in many cases where you want early return, it's an @Err so you can just use `?^`. I'm not convinced we want it for other cases.

Evidence · Strong evidence

The successful path in tokenizeGo descends through bounds checking, option lookup, duplicate detection, arity and value lookup. Each error branch pushes the remaining work farther right.

std/cli.av · tokenizeGo ↗

Current pattern · distilled from the tokenizer

lookup = (options, head, tokens) =>
  options.find((m) => m.names.has(head)) ?>
    undefined => @Err("unknown argument '${head}'")
    m =>
      tokens.get(m.name) ?>
        undefined => @Ok(m)
        _ => @Err("${head} was supplied more than once")

Candidate syntax · return is not implemented

lookup = (options, head, tokens) =>
  m = options.find((item) => item.names.has(head)) ?>
    undefined => return @Err("unknown argument '${head}'")
    found => found
  tokens.get(m.name) ?>
    undefined => ()
    _ => return @Err("${head} was supplied more than once")
  @Ok(m)

The second match and all later work remain at the function’s normal indentation. This small example isolates the control-flow change; the payoff grows as validation stages accumulate. It does not claim a line-count reduction.

Original recommendation · superseded where noted above

Prototype return value inside existing match arms. Judge it on the complete tokenizer before choosing extra Boolean or guard sugar. An if expression alone would not flatten the continuing path.

The cost

A new exit form adds control-flow semantics to the parser, checker and evaluator. It can also make an exit destination harder to see inside a callback unless the scope rule is strict.

Semantics to settle before implementation 4 points
Exit type
An exiting branch contributes no ordinary value to its enclosing match. Its payload constrains the function result. This needs an internal “does not continue” representation; a public Never type is not required by this proposal.
Nested lambdas
Return exits the nearest lambda, including collection callbacks. It must not jump out of the caller of map or flatMap.
Comprehensions and propagation
Specify whether record comprehensions are transparent to explicit return, and align this with their existing ?^ behavior. Do not accidentally introduce callback-style boundaries during lowering.
Guard spelling
If true => return …, false => () stays noisy, evaluate conditional-return sugar separately. No guard keyword or spelling is settled here.

What would establish successRewrite tokenizeGo with the same errors and token-consumption behavior. Verify result inference, annotated results, nested lambdas, comprehension exits, ?^ interaction, unreachable code and formatter behavior.

02
Specified, not implemented

Write generated text as text

Design the dedented form

Implement raw and multiline string literals already described by the spec. Settle exact whitespace behavior before converting the shell fragments.

After your review · Design the dedented form

Adopt your direction for the next design draft: content starts after the opening delimiter and ends before the closing delimiter; the closing delimiter sets the indentation removed. Prefer normalized LF line endings. Raw-literal spelling, delimiter collisions, blank lines and tabs remain the details to settle. See the sourced comparison below.

Your response

I'd like a review of what other languages do in this case. My preference is that triple quoted strings start on the line after the start """ and finish the line before the end """ and that the end """ indent indicates how many spaces to remove from each line. Anything indented less than the end """ is an error. I don't have a strong opinion on raw string syntax. I'll go with whatever is most common, I think but it should be extensible to other patterns, like with ruby strings where you can use a similar syntax to list an array of words. I don't recall the exact syntax, but I'm sure you know what I'm talking about. Whitespace - dedenting is wanted, as I've described above. Dedent to the level of the closing """. Line endings - I think normalized, but if there is a consensus in other languages, particularly the more recent ones, let's do what they do. Delimiter collisions - I'm happy to hear suggestions on this one. Formatter contract - hopefully I've made it clear - the closing """ determins the dedent level.

Evidence · Strong evidence

The generator now contains a larger shell scanner encoded as arrays of quoted, escaped lines. Reviewing Bash requires first mentally decoding Aven escapes. The misleading diagnostic recommending unavailable raw strings has already been fixed.

Language spec · String Literals ↗

Current syntax · representative shell fragment

body = [
  "  for item in \"\${candidates[@]}\"; do",
  "    COMPREPLY+=(\"$item\")",
  "  done"
].joinWith("\n")

Specified syntax · raw multiline, exact-preservation proposal

body = r"""  for item in "${candidates[@]}"; do
    COMPREPLY+=("$item")
  done"""

These two fragments are intended to produce identical text: no leading newline and no trailing newline. Starting and ending the content on the delimiter lines makes that explicit.

Original recommendation · superseded where noted above

Start with exact preservation of characters between the delimiters. Raw strings perform neither escape processing nor interpolation; ordinary triple-quoted strings retain both. Keep shell escaping helpers for dynamic values.

The cost

Exact preservation makes indentation visible but also makes reindenting literal content a semantic edit. Automatic dedenting improves presentation at the cost of another rule that can silently change generated bytes.

Semantics to settle before implementation 4 points
Whitespace
Preserve leading/trailing newlines and indentation exactly. If dedenting is wanted, give it a named library operation with its own contract rather than an invisible formatter transformation.
Line endings
Decide explicitly whether CRLF is preserved or normalized. Exact preservation implies preserving it; establish the rule through byte-level fixtures.
Delimiter collisions
The initial raw triple-quoted form cannot contain its closing delimiter. Hash delimiters remain a separate option if real generated text needs them.
Formatter contract
Formatting must preserve the literal’s value. Moving a raw block to a new scope must not silently add spaces to its content.

What would establish successImplement through lexing, parsing, checking, evaluation and formatting. Test escapes, interpolation, embedded quotes, whitespace and malformed literals. Convert static shell fragments and verify byte-equivalent output where intended.

03
Semantic change

Keep natural names available inside functions

Keep current behavior

Allow a function-local value to shadow a module-level value by default. Retain explicit rebinding for names already local to the function.

After your review · Keep current behavior

Confirmed by check and run: option := options[0] ?? "" inside render intentionally shadows the module-level option function. No language change is needed for the reported collision. The original proposal below is retained only as review history.

Your response

We have `:=` for variable shadowing. If that doesn't help in this case, I'd like to know about it.

Evidence · Concrete incident; policy tradeoff

Local option and command bindings collided with module constructors. The checker correctly diagnosed them; the repairs used entry and item. Larger modules reserve more natural local names under the current rule.

names.rs · accidental_shadowing_diagnostic ↗

Current workaround · illustrative declarations

option = (value) => value

render = (options) =>
  entry = options[0] ?? ""
  entry

Proposed rule · same value, natural local name

option = (value) => value

render = (options) =>
  option = options[0] ?? ""
  option

The module’s option function remains available outside render. Within render, the local binding wins after its declaration. This is lexical shadowing, not mutation.

Original recommendation · superseded where noted above

Relax only the module-value-to-function-local boundary initially. Preserve the requirement for := when replacing a parameter or existing local. Keep the current two-location diagnostic for collisions that remain illegal.

The cost

A local can hide a module helper the author intended to call. The gain is reduced naming pressure; the loss is one class of automatic mistake detection. Keeping today’s rule is a defensible alternative.

Semantics to settle before implementation 4 points
Same-function locals
Continue to reject a second ordinary binding with the same name. Keep := as creation of a new binding, not mutation.
Enclosing captures
Do not automatically exempt locals captured from an enclosing function. Decide that separately from module declarations.
Imports and builtins
Decide whether imported values receive the same treatment as local module declarations. Do not extend this recommendation to type names or builtin namespaces without separate review.
Recursion and initializer lookup
Specify whether a recursive local lambda shadows the module name in its own body. Preserve the existing special meaning of := initializers referring to the previous binding.

What would establish successCheck module values, parameters, ordinary locals, nested closures, imports and recursive helpers. Name resolution, inferred types, evaluator lookup, rename and LSP completion must agree.

04
Diagnostics and capability contract

Explain why comptime could not proceed

Promote correctness above diagnostics

Distinguish a dynamic input from an unsupported computation, and both from a failed evaluation. Avoid forcing library authors to redesign APIs around a generic error.

After your review · Promote correctness above diagnostics

The exact join(["a", "b"]) probe still fails with comptime.argument-not-known. Known values must be evaluable through ordinary helper calls; a broad intermediate type must not be mistaken for an unknown value. Fix that semantic gap first, then improve failure location and call-path reporting. This does not reopen completion delivery.

Your response

The example shouldn't fail since "a" and "b" are comptime known, even though join is not a comptime function. The point of the comptime function, or any comptime function for that matter is that they should be evaluatable at comptime - not that every part of the evaluate tree is comptime. That said, it would be nice if we got some indication at the comptime failure where the evaluation failed because something wasn't known at comptime. But that's a separate issue. The first above is more serious. This second one is a nice to have feature which we should address if we can, but can leave until later if it's very difficult.

Evidence · Historical probes; recheck required

The implementation note records failures for text computation and structured descriptors at comptime. The spec now promises evaluation of known arguments and lifting the evaluated result into its literal type. The working CLI proves shape-driven specialization more strongly than general execution.

Implementation note · comptime probes ↗

Historical probe · outcome must be rechecked at implementation time

join = (parts: Array(Text)): Text =>
  parts.joinWith("\n")

script = comptime(join(["a", "b"]))
# Recorded outcome: comptime.argument-not-known

Proposed diagnostic shape · wording, not an observed message

Cannot evaluate this call at compile time.

  script = comptime(join(["a", "b"]))
                    ^^^^^^^^^^^^^^^^

Reason: [specific unsupported operation or value]
Call path: comptime → join → [failing operation]

The inputs are known; this compiler capability is missing.

The bracketed reason is deliberately not invented. Reproduce the probe, inspect the failure stage, and emit this category only if the compiler has established that the input values are known.

Original recommendation · superseded where noted above

Record the failing stage and distinguish genuine runtime dependency, unsupported evaluation/representation, and evaluation failure or fuel exhaustion. Keep imported-source spans attached to the right file.

The cost

Better diagnostics require preserving evidence across inference and evaluation boundaries. Renaming a generic error without that evidence would make the message more confident rather than more accurate.

Semantics to settle before implementation 4 points
Dynamic input
Point to the value that depends on runtime information. A known static record shape is not proof that all record values are known.
Unsupported capability
Name the operation or representation that cannot cross the comptime boundary. Do not claim known inputs unless that has been established.
Evaluation failure
Retain panic/error details and the call path. Fuel exhaustion should report the budget and relevant trace, not masquerade as an unknown argument.
Scope
General comptime execution and residualization remain separate implementation projects. Runtime completion generation is settled and remains suitable.

What would establish successReproduce the recorded examples against current code, then add focused diagnostics for each actual failure class. Follow the spec’s error policy; do not silently fall back to runtime when required evaluation fails.

05
Optional language sugar

Give local error propagation a visible boundary

Defer special syntax

Consider an attempt-style expression that catches ?^ locally, avoiding an immediately invoked lambda whose only purpose is to delimit propagation.

After your review · Defer special syntax

Do not add an attempt keyword for this isolated case. Keep the existing lambda propagation boundary and mapErr. Revisit only if repeated real examples justify a keyword-free form; no replacement syntax is being proposed now.

Your response

This looks like a new keyword. We don't currently have any keywords so I wouldn't add one just for this. If this occurs a lot though, I'd consider special syntax.

Evidence · One clear use; lower priority

define wraps tokenization and descriptor reads in (() => …)() so their errors can be decorated with usage text before leaving the parser.

std/cli.av · define.parse ↗

Existing mechanism · shortened to show the boundary

result = (() =>
  tokens = tokenize(options, argv)?^
  @Ok({ keys -> key;
    (key, schema[key].read(tokens, key)?^) })
)()
result.mapErr((message) => "${message}\n\n${usage}")

Candidate syntax · attempt is not implemented

result = attempt
  tokens = tokenize(options, argv)?^
  @Ok({ keys -> key;
    (key, schema[key].read(tokens, key)?^) })

result.mapErr((message) => "${message}\n\n${usage}")

Both examples deliberately use mapErr, which already exists. The proposed benefit is the propagation boundary itself, not removal of an error-mapping match. Layout shown here is illustrative.

Original recommendation · superseded where noted above

Defer until the early-exit scope rules are settled. If adopted, keep an explicit Result as the final expression initially: successful completion yields that Result, and ?^ returns an error to this block’s boundary.

The cost

Another boundary can make the destination of ?^ surprising. A naive lambda desugaring would also change the destination of explicit return once that feature exists.

Semantics to settle before implementation 4 points
Return versus ?^
Recommended distinction: ?^ stops at the nearest attempt or function boundary; explicit return exits the nearest function. That means attempt is not simply a lambda once return exists.
Nested functions
A lambda inside attempt keeps its own propagation boundary. It must not propagate errors into a caller’s attempt block.
Successful result
Require a final compatible Result initially. Automatic @Ok wrapping is a separate choice, especially when the body already returns Result.
Evidence threshold
First try mapErr and existing function composition. Adopt a new form only if local propagation scopes recur beyond this one example.

What would establish successCompare the complete define.parse implementation, not just the shortened snippet. Verify nesting, mixed error types, explicit return, comptime behavior and formatter layout.

Follow-up / sourced language comparison

Closing-delimiter indentation has strong precedent.

Your rule closely matches Swift and C# raw multiline literals. There is no single consensus across all languages: others infer indentation from the content or preserve it until a library operation removes it.

LanguageIndentation and delimitersImplication for Aven
SwiftMultiline content lies between delimiter lines. The closing delimiter sets the required indentation prefix; additional indentation is retained. Physical line breaks normalize to LF.The closest overall precedent for your preferred rules. Nonblank lines must have the prefix; blank lines need a separate rule.
C#Raw multiline strings strip the closing delimiter’s indentation and exclude the adjacent boundary newlines. Too little content indentation is an error. More quote characters avoid delimiter collisions; source line endings are preserved.Supports your margin and error rule, but not the preference for newline normalization.
JavaText blocks require a newline after the opener, normalize line breaks, and remove incidental indentation using content and closing-delimiter placement. A closing delimiter on its own line normally leaves a final newline.Useful normalization precedent, but different indentation and final-newline behavior.
KotlinTriple quotes suppress backslash escapes but retain interpolation and indentation. trimIndent()/trimMargin() remove indentation explicitly and normalize separators to LF.The library-dedent alternative you rejected. It does not use the closing delimiter to enforce a minimum margin.
RubySquiggly heredocs (<<~) remove the least indentation in the content, not a margin defined by the terminator. Percent literals share delimiter machinery across strings, words, regexes and symbols.A useful extensibility model, but not the dedentation rule to copy.

Recommended Aven multiline rules

  1. Require a line break immediately after the opening triple quote, and put the closing triple quote on its own content-free line.
  2. Remove those two boundary line breaks from the value. Extra blank content lines remain observable.
  3. If the closer has N leading spaces, remove exactly N spaces from every nonblank content line. Reject a nonblank line with fewer.
  4. Normalize physical source line endings to LF, before interpreting escapes. An explicit \r in an ordinary string still requests a carriage return.
  5. Reindent the closing delimiter and all content lines together when formatting. Never reindent only one side of this contract.

One deliberate refinement to discuss: allow empty or whitespace-only lines shorter than the closing margin, yielding an empty line. Swift has a nonblank-line rule, and C# also treats blank lines specially. Requiring spaces on otherwise empty lines would make validity depend on editors preserving trailing whitespace. This is a recommendation, not a silent exception to your rule. For tabs, keep Aven’s existing layout policy and avoid display-column arithmetic; use spaces for the dedent margin.

Proposed Aven source

message = """
    first
      second
    """

Exact resulting value

"first\n  second"

There is no implicit trailing newline. To request one, include a blank content line before the closer (or an explicit escape in a non-raw literal).

Raw syntax and the Ruby form you remembered

%w[red green blue]     # Ruby: ["red", "green", "blue"]
%W[hello #{name}]      # Ruby: interpolated word array
%q{literal text}       # Ruby: non-interpolated string
%Q{hello #{name}}      # Ruby: interpolated string

Ruby’s percent literals are the family you mean. Its non-interpolated forms still have limited escaping; they are not identical to a Rust-style completely raw payload.

My preferred direction for Aven: retain r"…" and r"""…""", and use optional Rust-style hashes for delimiter collisions: r#"contains a " quote"#, r##"contains "#"##. A raw multiline variant such as r#""" … """# can use the same hash-count rule while keeping your dedentation semantics. These Aven spellings are proposals.

The r prefix has established precedents in Python and Rust; I cannot substantiate a claim that one raw spelling is universally “most common.” To preserve extensibility, define the grammar around a literal-kind prefix and a shared delimiter scanner. A future w"red green blue" could reuse that machinery without adding Ruby’s entire percent-literal family now. Word splitting, escapes and interpolation boundaries would still need their own semantics. If configurable bracket delimiters matter more than familiar r spelling, Ruby-style %q{…}/%w[…] is the coherent alternative.

LF normalization has strong precedent in Swift, Java, and Rust’s CRLF input normalization. C# differs, so this is a well-supported choice rather than a universal consensus.
